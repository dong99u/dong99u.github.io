    DERO ⑧남긴 큐

    이미지 생성기를 노트북에서 외부 API로 바꾸기로 한 날, 큐를 둔 첫 이유는 사라졌지만 서버가 재시작해도 작업을 잃지 않는다는 이유로 큐는 그대로 두었다.

    2026-07-31 설계 · 08-06 생성기 교체 · 08-18 휴면 · 10-12 삭제

    스크롤

    이미지 생성기는 공유기 안쪽의 노트북이 될 예정이었다.

    사용자가 책상 배치를 올리면 그 배치의 이미지를 생성하는 기능이었다. 2026-07-31 설계 문서는 생성기를 로컬 노트북에서 도는 프로그램으로 잡았다. 노트북에는 공인 주소가 없어서 서버가 노트북에 먼저 연결할 수 없었다.

    그래서 작업을 쌓아 두는 대기열, 큐를 골랐다.

    검토한 안방식판정
    A · gRPC 워커 풀노트북이 서버에 스트림을 열고 작업을 받아 간다.부결
    B · 터널로 노트북 노출터널을 두고 서버가 노트북을 직접 부른다.부결
    C · Redis 큐서버가 작업을 넣고 노트북이 꺼내 간다.채택
     큐는 업로드 요청을 쌓아 두고 뒤에서 하나씩 꺼내 처리하는 대기열이다. Redis를 고른 이유로 문서가 든 순서는 이미 배포돼 있다, gRPC 서버를 얹는 비용이 든다, 큐가 버퍼가 된다였다.

    꺼낸 작업은 처리중 목록에 남겨, 도중에 죽어도 잃지 않게 했다.

    구현한 날 실제로 붙인 생성기는 외부 API였다.

    2026-08-02 00:35에 큐와, 서버 안에서 큐를 비우는 스레드 1개짜리 워커를 구현했다. 1시간 7분 뒤인 01:42에 외부 이미지 API를 부르는 생성기를 붙였다. 노트북용 생성기 코드는 08-06 오전에 팀원이 저장소에 올렸다.

    2026-08-06 저녁, 노트북 기획을 파기했다.

    새 설계 문서가 생성기를 외부 API로 확정했다. 서버가 노트북에 연결할 수 없다는 제약은 노트북과 함께 없어졌다. 큐를 고른 핵심 제약이 사라진 것이다. 문서는 앞선 결정 12개 가운데 5개를 고치고 나머지는 유효하다고 적었다.

    결정 12개 가운데 5개를 고쳤고, 큐로 보낸다는 결정은 남은 쪽에 있었다.

    그날 큐 코드에서 바뀐 것은 주석 아홉 줄이다.

    큐에 대해 그날 문서가 적은 것은 한 문단이다.

    「결정 4의 유실 방지는 그대로 유지한다. 원인이 '노트북이 잠들었다'에서 'WAS가 재시작했다 / GMS가 늦다'로 바뀌었을 뿐 유실은 여전히 난다.」 생성기를 갈아 끼우는 추상화도 같이 남겼다. 지우면 키 없이 띄우는 로컬과 CI 부팅이 깨진다는 이유였다.

    큐 코드가 저장소에 있던 기간.

    71일

    2026-08-02에 구현했다. 08-18에 이미지 생성 기능을 휴면으로 돌리는 결정이 났고, 10-12에 팀원의 커밋으로 큐 141줄, 워커 100줄, 생성기 196줄이 삭제됐다.

    이 사례에는 측정값도 사고도 없다.

    확인되는 것은 언제 무엇을 결정했고 그때 코드가 어땠는가다. 서버가 재시작한 뒤 큐가 작업을 실제로 되살린 적이 있는지는 운영 로그를 볼 수 없어 모른다. 기능은 2026-08-18에 휴면이 됐고 코드는 10-12에 팀원의 커밋으로 삭제됐다.
