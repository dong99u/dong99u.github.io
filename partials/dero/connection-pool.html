서버는 DB와 통하는 연결을 몇 개만 열어 두고 돌려 쓴다. 이 묶음이 연결 풀이다.

이미지 생성 코드가 DB 연결을 쥔 채 외부 API의 응답을 기다렸다.

DB 작업 여러 개를 하나로 묶는 트랜잭션 안에서, 행을 먼저 고친 뒤 이미지 생성 API를 불렀다. 묶음이 끝날 때까지 연결은 풀로 돌아가지 않는다. 2026-08-02에 들어간 코드다.

그 대기는 얼마나 길어질 수 있었나.

900초

생성 API의 읽기 제한 시간 300초에, 업로드 한 번이 차례로 보내는 생성 요청 3번을 곱했다. 설정값으로 계산한 상한이고, 실제로 쥔 시간을 잰 값은 아니다.

나흘 뒤 들어온 제품 검색도 같은 모양이었다.

2026-08-06, 검색이 DB 조회, 검색 엔진(Elasticsearch) 조회, DB 조회를 한 트랜잭션으로 묶은 채 들어왔다. 이미지 쪽은 작업자가 하나라 연결을 1개까지만 쥐지만, 검색은 동시 요청 수만큼 쥘 수 있었다.

이 구조가 무슨 일을 내는지는 작은 프로그램으로 재 봤다.

고친 뒤인 2026-08-27자 프로그램이고, DERO 코드가 아니라 같은 모양을 흉내 낸 모형이다. 연결 10개와 외부 대기 300ms는 정한 값이다. 연결을 쥔 채 기다리는 쪽과 놓고 기다리는 쪽 옆에서 상관없는 조회 하나의 시간을 쟀다.

동시 요청 8개까지는 멀쩡했고, 16개에서 상관없는 조회가 느려졌다.

연결 10개에 동시 요청 16개일 때, 상관없는 조회 하나가 걸린 시간.

5초대

연결을 쥔 채 기다리면 중앙값이 1ms에서 5초대로 늘었다. 연결을 놓고 기다리면 같은 조건에서 1ms였다. 재현 프로그램의 값이다.

기다리는 호출 세 곳을 트랜잭션 밖으로 뺐다.
